Why build it in now

The penalties are real money.

The Act's Schedule (Section 33) sets the maximum penalty for each kind of breach. Even the line for "any other provision", which covers consent, notices, erasure and rights requests, goes up to ₹50 crore.

₹250 croreNot taking reasonable security safeguards to prevent a personal data breachSection 8(5) · Schedule item 1
₹200 croreNot notifying the Board and affected people of a personal data breachSection 8(6) · Schedule item 2
₹200 croreNot meeting the additional obligations for children's dataSection 9 · Schedule item 3
₹50 croreBreaking any other provision of the Act or the Rules: consent, notices, erasure, rightsSchedule item 7

The burden of proof is on you.

If consent is questioned, Section 6(10) makes the Data Fiduciary prove that a notice was given and consent was given. "consented: true" in a column isn't proof.

May 2027 is closer than it looks.

Notices, erasure, breach handling and rights requests all start then. Retrofitting them into a grown codebase takes longer than building them in now.

Spreadsheets drift.

A data map that lives outside the code is out of date the day someone adds a column. Compliance has to live where the changes happen: in the code and in CI.

Compliance that can't quietly drift

Someone adds a column. CI notices.

Most teams keep their data map in a spreadsheet, and six months later it's wrong. dpdp-kit reads your real Drizzle schema and fails the build when a personal-looking column has no declared purpose, or when the map points at columns that are gone.

    How it works
    
One config. Five things it does for you.

    


      

        

          
i.

          
Say why you hold each field.

          
Purposes, their legal basis and how long you keep the data live in one file. Purposes are typed, so a misspelt one is an error in your editor, and the audit catches the rest.

          The config, field by field →
        


// dpdp.config.ts
import { defineConfig } from "dpdp-kit";

export default defineConfig({
  fiduciary: { name: "Acme Pvt Ltd", grievanceUrl: "https://acme.in/grievance" },
  purposes: {
    account:       { basis: "legitimate-use", retain: "while-active" },
    marketing_sms: { basis: "consent", retain: { afterWithdrawal: "0d" } },
  },
  data: {
    users: {
      table: "users",
      subject: "id",
      fields: { phone: { category: "contact", purposes: ["account", "marketing_sms"] } },
    },
  },
  minimumRetention: "1y", // Rule 8(3)
});

      


      

        

          
ii.

          
Consent you can prove.

          
Section 6(10) puts the burden of proof on you. Every grant and withdrawal is stored with the notice version, language and channel, in a per-person SHA-256 hash chain.

          
verify() catches an edited, deleted or reordered event.

          How the record works →
        


await dpdp.consent.grant(userId, ["marketing_sms"], {
  noticeVersion: "2026-11",
  language: "hi",      // English or any of the 22 Eighth Schedule languages
  channel: "android",
});

await dpdp.consent.has(userId, "marketing_sms"); // true
await dpdp.consent.verify(userId);               // { ok: true, events: 1 }

      


      

        

          
iii.

          
Erasure that actually happens.

          
    
            
  • Processors are told to stop straight away.
    • 
            
  • A field is erased only when none of its purposes remain.
    • 
            
  • Rule 8(3)'s one-year minimum is respected.
    • 
            
  • Legal holds win: GST invoices wait 8 years, then get anonymised.
    • 
            
  • Safe with several servers: tasks are claimed atomically.
    • 
          

          Erasure and retention →
        


// a withdrawal schedules the erasure as dated tasks
await dpdp.consent.withdraw(userId, ["marketing_sms"]);

// an account deletion, with legal holds applied
await dpdp.erasure.deleteAccount(userId);

// then, from a daily cron:
const report = await dpdp.retention.run(); // { done, failed, manual }

      


      

        

          
iv.

          
Rights requests, on a clock.

          
Access, correction, erasure, grievance and nomination requests (Sections 11–14) are recorded with a due date. Grievances default to the 90 days of Rule 14(3).

          Rights requests →
        


const request = await dpdp.rights.open(userId, "grievance", {
  text: "I keep getting promo SMS",
}); // due in 90 days

await dpdp.rights.list({ overdue: true }); // your inbox of late answers
await dpdp.rights.summary(userId);         // Section 11: what you hold and why

      


      

        

          
v.

          
A GitHub Action that comments where it hurts.

          
Each problem lands on the pull request as an annotation, with a summary on the run page and errors / warnings outputs.

          Set it up →
        


# .github/workflows/dpdp.yml
on: [pull_request]
jobs:
  audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm ci
      - uses: yogesh2902/dpdp-kit@main
        with:
          schema: src/db/schema.ts

      Questions
      
Things people ask.

    

    

      
Does dpdp-kit make my app compliant?
No tool can do that on its own. dpdp-kit puts the obligations into practice in your code: declared purposes, consent records, erasure and rights requests. You still need a privacy notice, security safeguards and your own lawyer's review of your purposes and retention periods.

      
Is it free?
Yes. It's MIT licensed, with no paid tier and no account. You can use it in commercial products.

      
Do I need to run a server or sign up for anything?
No. It's a library that runs inside your Node.js process and writes to your own database. There's no API key, and it makes no network calls.

      
Which databases and frameworks does it support?
Storage and data access work with Postgres through Drizzle (node-postgres, postgres.js, Neon, PGlite). The schema drift check reads Drizzle schemas for Postgres, MySQL and SQLite. Guards are included for Express, Hono, Fastify and NestJS. Every store is an interface, so you can add another database; MySQL, SQLite and Prisma support are on the roadmap.

      
Which Node.js versions?
Node.js 20.19 or later. The package is ESM-only, and require("dpdp-kit") also works on those versions.

      
When do I need to have this in place?
The DPDP Rules were notified on 13 November 2025. Most obligations, including notices, erasure, breaches, children and rights requests, start in May 2027 (Rule 1). Starting now leaves time to test.

      
What if a legal reference is wrong?
Every reference was checked against the official texts of the Act, the Rules and their corrigendum, but laws change. Report it as a GitHub issue; it's treated as a bug.

      
How can I help?
Star the repo, try it in a project, and open issues for what's missing. Pull requests are welcome, especially for new database adapters.
